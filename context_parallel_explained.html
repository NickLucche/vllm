1. Why context parallel?

Context Parallel (CP) attacks the long-context problem: a single request whose sequence is too long to serve efficiently on the existing parallelism layout. Instead of sharding the model (weights, heads), CP shards along the token / sequence (T) dimension of one request.

vLLM treats prefill and decode separately, because they have opposite bottlenecks:

Prefill

Many query tokens, computed once. Goal: lower TTFT by amortizing the prefill compute across GPUs. → Prefill Context Parallel (PCP).

Decode

One query token per step, attending to a huge stored KV cache. Goal: more room for KV cache → bigger batch → throughput. → Decode Context Parallel (DCP).

The four parallelism axes

CP sits alongside the existing parallel dimensions. A useful mental model:

Key insight (from the deployment guide): TP can only shard the KV cache up to the number of KV heads H. Past that, tp_size / H copies of the KV cache are duplicated. DCP shards along T instead, reclaiming that wasted memory without launching more GPUs. Valid DCP range: [1, tp_size / H]. docs/serving/context_parallel_deployment.md

2. Prefill Context Parallel (PCP)

vllm/config/parallel.py · prefill_context_parallel_size

For a long prefill of T new tokens across N GPUs, vLLM splits the request into N chunks; each GPU computes Q/K/V for its chunk. There are two strategies:

Partial query, full K/V

When the sequence still fits: gather K/V from all GPUs, each GPU computes attention only for its query chunk. Accelerates prefill, lowers TTFT.

Partial query, partial K/V

When the sequence is too long to hold full K/V: keep only your chunk and stream K/V around the ring — ring attention.

Both PCP strategies are under active development. PCP is configured via --prefill-context-parallel-size (pcp_size).

3. Decode Context Parallel (DCP)

vllm/config/parallel.py · decode_context_parallel_size · CLI: -dcp

Decoding is auto-regressive: each step has a tiny query (1 token) attending to a large stored KV cache. So DCP's whole job is how to shard the paged KV cache across GPUs — and crucially, to do it so that the cache can keep growing token by token during decode while staying balanced.

vLLM solves this with an interleaving strategy along the T dimension (credited to Chao Hong / Moonshot, paper). Each new token is deterministically routed to one CP rank based on its position. That routing is exactly what cp_kv_cache_interleave_size controls.

Where the gain comes from: with DeepSeek-R1 (1 KV head under MLA), -tp 8 duplicates the KV cache 8×. Adding -dcp 8 shards it instead, giving ~8× more usable KV cache space → larger batch → higher throughput. The cost is extra cross-rank communication per decode step.

What does DCP do during prefill? (e.g. -tp4 -dcp4, no PCP)

A common point of confusion: if DCP is a decode feature, what happens to the prefill phase when you launch with only -tp4 -dcp4? The short answer: prefill compute is not parallelized across the sequence — every DCP rank still processes the full prefill query. DCP only changes where the KV gets stored. You get DCP's memory benefit during prefill, but not a TTFT/compute benefit (that would be PCP, which you didn't set).

StepWhat happens under DCP-only prefillSource
Query Replicated, not split. Since PCP=1, there is no query-chunking; the query is all-gathered so each rank works on the whole prefill. flash_attn.py:984 — all_gather(query, dim=1)
KV write Sharded — this is the real effect. The slot-mapping marks each token is_local only on its owning rank and returns PAD_ID=-1 elsewhere; reshape_and_cache_flash skips -1 slots. KV is first created during prefill, so that's exactly when de-duplication must happen. block_table.py:368
Attention Stays correct via a two-phase scheme: a new-token phase (local causal self-attention over this batch's K/V) + a context phase (each rank attends to its local KV shard, then ranks combine via an LSE all-gather + reduce-scatter). The KV cache itself is never all-gathered — only the small LSE/output tensors move. ops/common.py:199 (cp_lse_ag_out_rs)
The cost: because the query is replicated, each rank redundantly computes attention for the full query against its KV shard — prefill FLOPs aren't reduced, and you pay extra all-gather/LSE communication per layer. So -dcp 4 during prefill means "pay a little extra comm to store KV sharded," not "make prefill faster."
Caveat for tp4 dcp4: the useful DCP range is [1, tp_size / H] where H = KV heads. tp4 dcp4 only makes sense when H = 1 (an MLA model like DeepSeek-R1 / Kimi). For a model with, say, 4 KV heads, tp/H = 1, so TP alone already shards the KV with zero duplication and DCP buys nothing — even though tp % dcp == 0 passes the hard assertion.

Combining PCP & DCP: the unified rank

When both are active, vLLM flattens them into a single total CP coordinate. Every token is owned by exactly one total_cp_rank:

total_cp_world_size = pcp_world_size × dcp_world_size total_cp_rank    = pcp_rank × dcp_world_size + dcp_rank

Everything below uses total_cp_world_size (abbreviated CP in diagrams) and total_cp_rank. With DCP alone, total_cp_world_size == dcp_world_size.

Why two knobs and not one?

A natural question: a request flows through prefill and then decode — why isn't CP a single number? Because PCP and DCP are physically different operations on different resources. The decisive line in the config makes it concrete:

vllm/config/parallel.py:784 
world_size = pipeline_parallel_size * tensor_parallel_size * prefill_context_parallel_size
# note: decode_context_parallel_size does NOT appear here
PCP multiplies the world size — it adds GPUs. DCP does not appear at all — it reuses the TP group's existing GPUs (tp_size % dcp_size == 0). One knob is impossible: it would have to mean "add GPUs" and "don't add GPUs" at the same time.

That asymmetry isn't an implementation quirk — it falls directly out of what each phase needs:

Prefill CPDecode CP
Bottleneck compute (TTFT) — thousands of query tokens at once memory (KV capacity) — 1 query token, huge stored KV
What you split the Q/K/V computation of new tokens the stored KV cache along T
GPUs adds them (world_size ×= pcp) reuses TP GPUs (no new GPUs)
Goal more FLOPs on the prefill in parallel kill the tp_size/H KV duplication → bigger batch

The phases pull on opposite resources, so fusing them would force you to over-provision one to satisfy the other:

  • Prefill is compute-bound — a wall of query tokens, so more GPUs (PCP) directly cut TTFT. There is real work to parallelize.
  • Decode is memory-bound — only one query token per step, so adding GPUs to compute it buys nothing. That's exactly why DCP is capped at tp_size/H. What you want is to stop wasting memory on duplicated KV — DCP shards the cache in place on GPUs you already have.

The one thing they do share: the KV layout

Once a token's KV exists, it must be stored somewhere consistent so that decode can find it later. That storage routing genuinely is a single knob — cp_kv_cache_interleave_size — applied over the flattened total_cp_world_size. This is why the older dcp_kv_cache_interleave_size is being deprecated in favour of the unified cp_kv_cache_interleave_size: the layout knob unifies even though the parallelism knobs cannot.

Mental model: two knobs for "how do I parallelize the work" (the work is different in each phase) + one knob for "how do I lay out the resulting KV cache" (the cache is shared across phases).

4. cp_kv_cache_interleave_size

vllm/config/parallel.py:351

This single integer decides the granularity at which consecutive tokens are handed out to CP ranks. The rule, straight from the source docstring:

Store interleave_size tokens on total_cp_rank i, then store the next interleave_size tokens on total_cp_rank i+1, wrapping around.

The owning rank for a token at virtual-block offset o is simply:

owner_rank(o) = (o // interleave_size) % total_cp_world_size

Two extremes matter, and the config supports anything in between (as long as it divides block_size):

ValueAlignmentBehaviour
1 (default)token-level Pure round-robin: token i → rank i % CP. Finest balance.
block_sizeblock-level Fill rank i's whole block before moving to rank i+1.
k (between)chunk-level Hand out k-token chunks round-robin. Must divide block_size.

For the diagrams below: total_cp_world_size = 4 block_size = 4 ⇒ virtual_block_size = block_size × CP = 16. A "virtual block" is the span of global token positions that maps onto one physical block on each of the 4 ranks.

interleave = 1 favours balance. Every rank gets near-equal KV regardless of sequence length — ideal for many short/odd-length requests and even compute across ranks.
interleave = block_size favours locality. Contiguous tokens sit together, which can simplify some attention kernels / reduce fragmentation, at the cost of load imbalance for short sequences. Required > 1 only with specific backend support (e.g. some MTP paths).

5. The slot-mapping kernel

vllm/v1/worker/block_table.py:325 · _compute_slot_mapping_kernel (Triton)

This is where the formula actually runs. For every token position pos in the batch, the kernel computes (a) which rank owns it and (b) where in that rank's physical KV cache it goes. Tokens not owned by the local rank are written as PAD_ID (skipped).

# total_cp_world_size = pcp_world_size * dcp_world_size
# total_cp_rank      = pcp_rank * dcp_world_size + dcp_rank
virtual_block_size = block_size * TOTAL_CP_WORLD_SIZE        # 4 * 4 = 16

block_indices  = pos // virtual_block_size                  # which virtual block
block_numbers  = block_table[req, block_indices]            # physical block id

virtual_block_offsets = pos - block_indices * virtual_block_size

# (a) does THIS rank own the token?
is_local = (virtual_block_offsets // CP_KV_CACHE_INTERLEAVE_SIZE) \
              % TOTAL_CP_WORLD_SIZE == TOTAL_CP_RANK

# (b) local slot within this rank's physical block
local_block_offsets = (
    virtual_block_offsets // (TOTAL_CP_WORLD_SIZE * CP_KV_CACHE_INTERLEAVE_SIZE)
) * CP_KV_CACHE_INTERLEAVE_SIZE + (
    virtual_block_offsets % CP_KV_CACHE_INTERLEAVE_SIZE
)

slot_ids = block_numbers * block_size + local_block_offsets
slot_ids = where(is_local, slot_ids, PAD_ID)               # skip non-owned tokens

Worked trace — token pos = 9, interleave = 1, CP = 4, block_size = 4

virtual_block_size4 × 4 = 16
block_indices9 // 16 = 0
virtual_block_offsets9 - 0 = 9
owner rank(9 // 1) % 4 = 1 → only rank 1 stores it
local_block_offsets (on rank 1)(9 // 4)×1 + (9 % 1) = 2

⇒ token 9 is the 3rd token (slot 2) in rank 1's block — matching the Mode A diagram above (rank 1 holds tok 1, 5, 9, 13).

Same token with interleave = 4 (= block_size)

owner rank(9 // 4) % 4 = 2 → rank 2
local_block_offsets(9 // 16)×4 + (9 % 4) = 0 + 1 = 1

⇒ token 9 is slot 1 in rank 2's block — matching the Mode B diagram (rank 2 holds tok 8, 9, 10, 11).

6. Per-rank sequence lengths during attention

vllm/v1/attention/backends/utils.py:862 · get_dcp_local_seq_lens()

Because tokens are spread unevenly when a sequence length isn't a multiple of CP × interleave, each rank may hold a slightly different number of KV tokens. The attention backend needs the exact local count per rank to size its work. That's this helper:

base = (seq_len // interleave // dcp_size) * interleave
remainder = seq_len - base * dcp_size
remainder = clip(remainder - rank * interleave, 0, interleave)
local_seq_len = base + remainder

Intuition: base is the evenly-divisible part every rank gets; the leftover remainder tokens form one last partial round, handed out interleave tokens at a time to the lowest ranks first.

Example — seq_len = 22, dcp_size = 4, interleave = 1

base = (22//1//4)*1 = 5; total remainder = 22 - 5×4 = 2, given to ranks 0 and 1. Sum = 6+6+5+5 = 22. ✓ The backend also derives the max workspace as ceil(seq_len / (dcp_size×interleave)) × interleave (see flash_attn.py / mla_attention.py).

Validation (enforced at startup)

vllm/config/vllm.py:2143 
assert (interleave <= block_size) and (block_size % interleave == 0), \
    "Block_size should be >= and divisible by cp_kv_cache_interleave_size"

So cp_kv_cache_interleave_size ∈ {divisors of block_size that are ≤ block_size}. With block_size = 16: valid values are 1, 2, 4, 8, 16.

Compatibility is also checked in vllm/v1/worker/cp_utils.py: DCP requires attention backends that return LSE (log-sum-exp) so partial attention outputs can be combined across ranks; speculative decoding (MTP) with interleave > 1 needs special support.
